# 《中级船体装配工工艺学》知识图谱与 RAG 系统实验报告

## 第1章 绪论

### 1.1 作业背景与研究意义

本项目来源于“知识工程与知识自动化”课程作业。课程要求围绕具体领域文档完成数据预处理、知识图谱本体设计、知识抽取、知识图谱存储管理、可视化展示以及基于知识图谱的智能问答系统设计与评测。与通用问答任务不同，工业工艺类知识具有强领域性、强流程性和强证据依赖等特点。例如船体装配教材中包含大量构件名称、装配方式、工艺步骤、图纸资料、测量指标、质量标准和焊接变形控制措施，单纯依赖关键词检索或普通大模型问答容易出现证据定位不准、关系链路不清和回答不可追溯等问题。

知识图谱能够将教材中的“实体-关系-实体”知识显式组织起来，使分段类型、船体构件、工艺工序、工装设备和质量控制措施之间形成结构化连接。对于船体装配这类工艺知识，知识图谱的价值主要体现在三个方面：第一，可以把分散在教材不同段落中的工艺对象和工艺步骤关联起来，形成可查询、可分析的知识网络；第二，可以支持装配流程、构件组成、质量控制和标准指标等关系型问题的推理和追溯；第三，可以为后续智能问答系统提供结构化证据，减少大模型直接生成时的幻觉风险。

大模型在本项目中主要承担两类任务。一类是知识自动化构建任务，即根据设计好的本体和 Prompt 从教材文本中抽取实体和三元组；另一类是 RAG 问答任务，即在检索到相关文本块和图谱三元组后，生成可读、可追溯的答案。RAG 技术将外部知识库检索与大模型生成结合起来，能够缓解大模型参数知识过时、领域知识不足和答案缺少出处的问题。本项目进一步采用 Graph-RAG 思路，将向量检索得到的教材原文证据与图谱检索得到的结构化三元组证据结合，使系统既能回答“某个概念是什么”，也能回答“某个工艺流程包括哪些步骤”“某种装配方式适用于什么对象”“某项质量标准如何控制”等更适合结构化知识表达的问题。

### 1.2 语料来源与实验范围

本项目的核心语料来源为《中级船体装配工工艺学》扫描版教材，对应原始文件为 `中级船体装配工工艺学_11934890.pdf`。项目首先对整本书进行了 PDF OCR、文本清洗、分块、知识抽取和 RAG 系统探索，形成了整本书级别的知识图谱和问答系统基础。整本书预处理结果保存在 `data/processed/` 目录下，包括逐页清洗文本、整书 Markdown、RAG/知识抽取文本块和预处理元数据。根据 `data/processed/README.md` 中记录，整本书共处理 192 页，生成 230 个面向 RAG 和知识抽取的文本块，平均 OCR 置信度约为 0.808。

在整本书探索的基础上，本文进一步选择第五章“船体分段的装配”作为重点章节开展精细化实验。选择第五章的原因主要有三点。第一，第五章文本主题集中，围绕船体分段装配展开，内容边界相对清晰，适合进行高质量本体设计和人工标注。第二，第五章同时包含装配方式、分段类型、构件组成、图纸资料、测量定位、双层底分段、舷侧分段、艏艉分段和质量控制等内容，知识类型较完整，能够覆盖知识图谱构建所需的多种实体和关系。第三，第五章中存在大量流程类和标准类知识，例如横骨架式舷侧分段装配程序、双斜切胎架定位、分段制造精度标准等，非常适合检验 Graph-RAG 相比纯向量 RAG 在结构化关系表达方面的价值。

因此，本文实验范围分为两个层次：一是整本书级探索，用于证明系统具备从扫描教材到知识图谱和 RAG 系统的规模化构建能力；二是第五章精细化实验，用于在较高质量文本和人工标注集基础上，对 Pangu、DeepSeek 两种抽取模型和三种 RAG 实现方案进行更可信的评测与对比。

### 1.3 本文主要工作

本文围绕《中级船体装配工工艺学》完成了以下工作。

第一，完成整本书级知识抽取与 RAG 系统初步探索。项目对整本书 PDF 进行了 OCR、格式转换、清洗和分块，随后使用 Pangu 7B 自部署模型抽取实体和三元组。整本书级 Pangu 图谱最终形成 1003 个实体和 1747 条关系，初步验证了从教材到知识图谱再到 RAG 问答系统的完整技术路线。

第二，完成第五章文本预处理和知识图谱构建。项目将第五章“船体分段的装配”整理为独立文本文件 `chapter5_rag/第五章.txt`，并切分为 29 个 chunk，保留 chunk_id、章节标题、页码范围、正文内容和字符数等元数据。基于该语料分别构建了 Pangu 版本和 DeepSeek 版本第五章知识图谱，其中 Pangu 第五章完整图谱包含 205 个实体和 257 条关系，DeepSeek 第五章完整流程图谱包含 192 个实体和 335 条关系。

第三，基于人工标注集评测 Pangu 与 DeepSeek 的知识抽取质量。项目从第五章 29 个 chunk 中选取 5 个代表性 chunk，人工标注 93 个实体和 79 条三元组，作为 gold 标准集。随后对 Pangu 和 DeepSeek 的第一轮、第二轮抽取结果进行实体级、三元组级、JSON 合法率、抽取成功率、证据支撑率和幻觉率评测。

第四，对比纯向量 RAG、Pangu Graph-RAG 和 DeepSeek Graph-RAG 的性能指标与成本。项目构造了 15 个第五章测试问题，覆盖概念定义、工艺流程、对比、图纸资料、质量控制和表格数据六类问题，对三种方案进行检索性能、图谱结构质量和构建成本对比。

## 第2章 数据预处理与实验语料构建

### 2.1 整本书语料处理探索

整本书原始语料为扫描版 PDF，无法直接得到结构化文本。项目首先使用 PyMuPDF 将 PDF 页面渲染为图像，再使用 RapidOCR 进行中文 OCR 识别，随后对 OCR 文本进行清洗和规范化。整本书预处理的主要流程包括：

1. PDF 页面读取与图像渲染：逐页读取扫描版 PDF，将页面转换为适合 OCR 识别的图像。
2. OCR 识别：使用 RapidOCR 对每页图像进行中文文本识别，得到页面级文本行和置信度信息。
3. 文本清洗：去除明显噪声、异常空白、页眉页脚、页码和重复行，规范换行与段落。
4. 章节提示构造：根据文本中的章节标题、图号、表号和上下文信息，为文本块保留章节线索。
5. 文本分块：将清洗后的逐页文本进一步切分为适合知识抽取和 RAG 检索的 chunk。
6. 产物保存：输出逐页 JSONL、整书 Markdown、文本块 JSONL 和预处理元数据。

整本书预处理产物包括 `ship_textbook_pages.cleaned.jsonl`、`ship_textbook.cleaned.md`、`ship_textbook_chunks.jsonl` 和 `preprocess_metadata.json`。其中 `ship_textbook_pages.cleaned.jsonl` 保存逐页清洗结果，`ship_textbook_chunks.jsonl` 保存面向 RAG 和知识抽取的分块结果，`ship_textbook.cleaned.md` 便于人工检查整本书文本，`preprocess_metadata.json` 记录页数、字符数、分块数和 OCR 置信度等元信息。

整本书处理过程中遇到的主要难点包括以下几类。第一，教材为扫描图像型文档，OCR 质量受页面清晰度、字体、表格线和图注干扰影响较大。第二，教材中图表较多，图号、表号、公式、编号和正文混排，容易造成文本顺序错乱或字段丢失。第三，不同章节主题差异较大，既有工艺流程，也有测量、放样、焊接、修理等内容，知识粒度不统一。第四，整本书层面存在大量章节标题、图注和表格数据，直接进行知识抽取容易产生泛化关系和重复节点，需要后续通过本体约束、Prompt 设计和实体归一化进行控制。

### 2.2 第五章精细化文本整理

第五章“船体分段的装配”是本文重点实验章节。与整本书探索相比，第五章语料经过了更细致的人工校验和清洗。项目将第五章内容整理为 `chapter5_rag/第五章.txt`，在此基础上去除了明显 OCR 错误、页码、无关图注干扰、重复换行和不完整段落，使文本更适合大模型进行结构化抽取。

第五章内容覆盖分段装配概述、装配方式分类、分段工作图、分段装配相关数据、双层底分段装配、舷侧分段装配、艏艉分段装配以及提高分段制造质量的措施等内容。清洗时特别保留了对知识抽取有价值的信息，例如“正装、倒装、侧装、卧装”等装配方式，“放射式、插入式、框架式、子分段组装式”等装配程序分类，“内底板、外板、纵骨、肋板、舷侧纵桁”等船体构件，以及“胎架支柱高度、定位数值、分段制造精度标准、焊接变形控制”等质量和数据指标。

第五章精细化整理的目标不是简单得到可读文本，而是形成适合知识图谱构建的实验语料。因此在整理过程中尽量保留工艺流程的完整顺序、表格指标的核心字段、构件与工序之间的上下文关系，以及能够作为 evidence 的原文短句。这样做可以提高后续实体抽取、三元组抽取和证据校验的可靠性。

### 2.3 文本切块与元数据设计

第五章清洗文本被切分为 29 个 chunk，保存于 `chapter5_rag/data/chapter5_chunks.jsonl`。每个 chunk 保留以下元数据：

- `id`：文本块编号，例如 `chapter5_001`、`chapter5_012`。
- `source`：来源文件，即第五章清洗文本。
- `page_start` / `page_end`：对应页码范围。
- `chapter_hint`：章节标题或小节提示。
- `text`：正文文本。
- `char_count`：字符数。

切块时采用中等长度文本块策略，单个 chunk 尽量保持一个相对完整的知识单元，例如一个小节、一个装配流程、一组图纸资料说明或一段质量标准说明。项目早期命令中使用过约 850 字符、100 字符重叠的切分思路，目的是在控制大模型输入长度的同时，尽量避免跨段落知识被割裂。对于 RAG 检索而言，较完整的 chunk 有助于提高上下文可读性；对于知识抽取而言，保留 chunk_id 和章节标题可以让三元组中的 evidence 追溯到原始文本块。

元数据设计对后续实验具有重要作用。首先，chunk_id 是人工标注、知识抽取、图谱构建、RAG 检索和评测指标之间的共同索引。其次，chapter_hint 可以辅助大模型理解当前文本块主题，减少实体类型误判。再次，page_start 和 page_end 能够支持答案引用页码和证据追溯。最后，char_count 有助于分析 chunk 长度对抽取失败和 JSON 输出截断的影响。

## 第3章 知识图谱本体设计与抽取方法

### 3.1 知识图谱本体设计

针对船体分段装配领域，本文设计了面向工艺知识组织的知识图谱本体。第五章人工标注和 round2 抽取中使用的实体类型主要包括：

| 实体类型 | 含义 | 示例 |
|---|---|---|
| 分段类型 | 船体分段或结构单元类型 | 双层底分段、舷侧分段、平直分段、球鼻艏分段 |
| 装配方式 | 分段装配时采用的位置状态或组织方式 | 正装、倒装、侧装、卧装、放射式、插入式、框架式 |
| 船体构件 | 船体结构构件或零部件 | 内底板、外板、纵骨、肋板、舷侧纵桁、甲板边板 |
| 工装设备 | 装配、定位、测量或施工设备 | 胎架、双斜切胎架、活络支柱胎架、千斤顶、松紧螺丝 |
| 工艺工序 | 装配流程中的具体工序 | 装配画线、焊接、封底焊、二次除锈涂装、完工检验 |
| 图纸资料 | 指导施工和装配的数据资料 | 分段工作图、板材号料图、外板加工图、分段组立树 |
| 质量问题 | 工艺过程中可能出现的问题 | 焊接变形、局部变形、尺寸偏差 |
| 控制措施 | 用于质量控制和缺陷修正的方法 | 刚性固定、补偿、火工矫正、完工测量 |
| 数据指标 | 表格标准、尺寸、数值和测量指标 | 分段长度、分段宽度、对角线、标准范围、允许界限 |
| 其他 | 不适合归入上述类型但具有知识价值的对象 | 中心线、中间肋骨线等 |

该本体的设计目标是既覆盖教材中的主要知识对象，又避免实体类型过细导致抽取困难。对于船体装配这种工艺教材，实体类型不仅要包含静态对象，如构件和设备，也要包含动态过程，如工序和装配方式，还要包含质量控制和数据标准。

### 3.2 关系类型设计

关系类型用于描述实体之间的语义连接。本文在人工标注模板和 Prompt 中建议并使用了以下关系类型：

| 关系类型 | 含义 | 示例 |
|---|---|---|
| 包括 | 表示概念、流程或资料包含子项 | 分段装配方式 包括 正装 |
| 属于 | 表示分类归属 | 双层底分段 属于 立体分段 |
| 可采用 | 表示某对象可以采用某方式 | 双层底分段 可采用 倒装 |
| 适用于 | 表示方法或设备适用对象 | 放射式 适用于 大型船舶纵骨架式双层底 |
| 用于 | 表示工具、图纸或措施的用途 | 分段工作图 用于 指导装配 |
| 指导 | 表示图纸资料对施工的指导作用 | 分段组立树 指导 装配程序 |
| 依据 | 表示工序或数据的依据来源 | 胎架支柱高度 依据 型值 |
| 组成 | 表示构件组成关系 | 双层底分段 组成 内底板 |
| 装配于 | 表示构件或分段的装配位置 | 肋板 装配于 内底板 |
| 连接 | 表示构件之间连接关系 | 舷侧纵桁 连接 肋骨 |
| 定位 / 对准 | 表示定位和对准关系 | 板角 定位 x、y 值 |
| 控制 | 表示质量控制关系 | 刚性固定 控制 焊接变形 |
| 导致 | 表示原因结果关系 | 焊接热输入 导致 焊接变形 |
| 校正 | 表示修正缺陷关系 | 火工矫正 校正 变形 |
| 代表 / 反映 / 表达 | 表示图纸、数据和结构之间的表达关系 | 分段组立树 反映 装配程序 |
| 标准范围 / 允许界限 | 表示表格标准数据 | 分段长度 标准范围 ±4mm |

这些关系既包括通用层级关系，也包括船体装配领域中的工艺关系和质量控制关系。后续评测中发现，关系归一化是影响三元组 strict F1 的关键因素之一：模型常常能够抽到语义接近的关系，但表达形式与 gold 标注不完全一致，例如“采用”“可采用”“可以是”“装配方式”等需要进一步归一化。

### 3.3 Pangu 知识抽取方案

Pangu 方案使用远程自部署的 Pangu 7B 模型进行实体和三元组抽取。项目中通过 HTTP 服务调用 Pangu 模型，并在 Prompt 中明确要求模型只根据输入文本抽取知识，不引入外部常识。Pangu 抽取流程主要包括以下步骤：

1. 输入第五章或整本书 chunk 文本，并附带 source_chunk、source_page 和 chapter_hint。
2. Prompt 中给定实体类型、关系类型和 JSON 输出 schema。
3. 要求每个实体和三元组包含 evidence 字段，用于后续证据追溯。
4. 解析模型输出 JSON，记录 raw_response、entities 和 triples。
5. 对实体和三元组进行清洗、去重、低置信度过滤和图谱文件生成。
6. 将图谱输出为 JSONL 文件，并可进一步导入 Neo4j 或用于 Graph-RAG 检索。

整本书级 Pangu 抽取产物保存在 `pangu/outputs/`，最终图谱摘要显示：整本书抽取 raw rows 为 224，形成 1003 个实体、1747 条关系，孤立实体 33 个。第五章完整 Pangu 图谱保存在 `chapter5_rag/outputs/graph/`，包含 205 个实体和 257 条关系，其中高连接节点包括“第五章船体分段的装配”“分段装配”“双层底分段”“焊接变形”“胎架”等，说明图谱能够围绕章节主题形成较集中的知识网络。

### 3.4 DeepSeek 知识抽取方案

为了与 Pangu 方案进行对比，项目将知识抽取模型替换为 DeepSeek，并尽量保持相同语料、相同本体和相同评测标准。DeepSeek 方案仍然以第五章 chunk 为输入，使用相同的实体类型、关系类型和 JSON schema，输出 raw_extractions、kg_entities 和 kg_triples 文件。

第五章完整 DeepSeek 流程图谱保存在 `chapter5_rag/deepseek_outputs/graph/`，摘要显示 DeepSeek 处理 29 个 chunk，失败 chunk 为 0，形成 192 个实体和 335 条关系，孤立实体 1 个。从完整图谱规模看，DeepSeek 抽取关系数量更多，图谱连通性更强。但在人工标注的 round2 评测中，DeepSeek 在 `chapter5_012` 上出现 JSON 不完整问题，导致 JSON 合法率和抽取成功率为 80%。这说明 DeepSeek 在语义覆盖方面更强，但结构化输出稳定性需要额外机制保障。

### 3.5 Prompt 优化策略

项目进行了两轮知识抽取实验。第一轮 Prompt 较为基础，主要要求模型抽取实体和三元组，并输出 JSON。第一轮结果显示，模型输出较保守，每个 chunk 抽取的实体和三元组数量较少，导致召回率偏低。以人工标注集为标准，第一轮 Pangu 平均每个 chunk 抽取 4.6 个实体、4.4 条三元组；DeepSeek 平均每个 chunk 抽取 5.0 个实体、5.6 条三元组。

第二轮 Prompt 针对第一轮问题进行了优化。优化策略包括：

1. 明确要求每个 chunk 抽取 12-15 个重要实体和 10-20 条重要三元组。
2. 强化 evidence 字段，要求每条三元组必须有原文短句或表格行作为证据。
3. 增加表格数据抽取要求，特别是标准范围、允许界限和数值指标。
4. 对枚举项进行拆分，例如“正装、倒装、侧装、卧装”需要分别形成实体或三元组。
5. 对流程文本进行拆分，例如“外板拼接--焊接--装配画线”需要抽取多个“装配程序包括”关系。
6. 强化 JSON 输出约束，要求只输出 JSON，不输出 Markdown 和解释文字。

优化后，Pangu 平均每个 chunk 抽取 15.0 个实体、16.2 条三元组；DeepSeek 平均每个 chunk 抽取 15.6 个实体、22.0 条三元组。可见第二轮 Prompt 显著提升了抽取覆盖度，但也带来了实体粒度不一致、关系表达不统一和 JSON 截断等新问题。

## 第4章 知识图谱构建与 Graph-RAG 系统实现

### 4.1 系统总体架构

本项目系统总体架构包括六个层次：

1. 数据预处理层：负责 PDF OCR、文本清洗、章节整理、chunk 切分和元数据生成。
2. 知识抽取层：调用 Pangu 或 DeepSeek 模型，根据本体和 Prompt 抽取实体与三元组。
3. 知识图谱构建层：对模型输出进行 JSON 解析、实体清洗、三元组清洗、去重、证据保留和图谱文件生成。
4. 向量检索层：对第五章文本块进行向量化，并写入 Qdrant 或本地向量存储，支持问题到文本块的相似度检索。
5. 图谱检索层：根据问题中的关键词、实体和关系线索，从知识图谱中检索相关实体与三元组。
6. 问答生成层：将文本块证据和图谱三元组证据共同组织为上下文，调用大模型生成答案，并返回检索证据和智能体执行链路。

第五章系统还实现了多智能体协同流程，包括 PlannerAgent、VectorAgent、GraphAgent、FusionAgent、AnswerAgent 和 VerifierAgent。PlannerAgent 负责分析问题类型，VectorAgent 负责文本检索，GraphAgent 负责图谱检索，FusionAgent 负责证据融合，AnswerAgent 负责答案生成，VerifierAgent 负责检查答案是否有证据支撑。前端界面中将 RAG 问答、智能执行链路和检索证据拆分为不同标签页，便于展示系统处理过程。

### 4.2 知识图谱构建流程

第五章知识图谱构建流程如下：

1. 从 `chapter5_chunks.jsonl` 读取 chunk 文本和元数据。
2. 对每个 chunk 调用 Pangu 或 DeepSeek 抽取实体与三元组。
3. 保存原始响应到 `raw_extractions.jsonl`，便于后续复查模型输出。
4. 解析 JSON，提取实体列表和三元组列表。
5. 对实体名称、类型、关系、source_chunk、source_page 和 evidence 进行规范化。
6. 过滤空实体、空关系、自环关系和不符合 schema 的输出。
7. 生成实体文件和三元组文件。
8. 计算图谱摘要，包括实体数、关系数、类型分布、孤立实体数和高连接节点。

项目采用 JSONL / JSON 文件作为图谱基础存储形式。实体文件保存每个实体的名称、类型、定义、来源页码、来源 chunk 和置信度；关系文件保存 head、relation、tail、evidence、source_chunk、source_page 和置信度；summary 文件保存图谱规模和结构统计信息。

### 4.4 Graph-RAG 问答系统设计

第五章 Graph-RAG 系统将文本向量检索和图谱三元组检索结合起来。系统接收用户问题后，首先使用向量检索从第五章 chunk 中召回相关文本块；随后使用图谱检索找到与问题相关的实体、关系和三元组；再由证据融合模块将文本证据和图谱证据进行合并、去重和排序；最后将融合后的上下文输入大模型生成答案。

与纯向量 RAG 相比，Graph-RAG 的优势在于能够显式利用结构化知识。例如用户询问“双层底分段的装配流程是什么”，向量检索可以召回包含流程描述的原文块，而图谱检索可以补充分段、构件、工序和装配关系；用户询问“焊接变形如何控制”，图谱检索可以直接返回“刚性固定--控制--焊接变形”“补偿--控制--焊接变形”“火工矫正--校正--变形”等结构化证据。这样生成答案时既有原文依据，也有关系链路。

项目中还实现了纯向量 RAG 基线方案 `vector_baseline_app.py`，该方案不读取、不构建、不使用任何知识图谱，只依赖第五章文本块向量检索结果生成答案。该基线用于衡量知识图谱增强相对于纯文本检索的增益。

## 第5章 知识抽取质量评测

### 5.1 人工标注集构建

为了客观评测知识抽取质量，项目从第五章 29 个 chunk 中选取 5 个代表性 chunk 构建人工标注集，覆盖不同内容类型：

| chunk_id | 内容主题 | 实体数 | 三元组数 |
|---|---|---:|---:|
| chapter5_001 | 分段装配概述与装配方式分类 | 16 | 15 |
| chapter5_005 | 分段工作图及相关资料 | 16 | 15 |
| chapter5_012 | 舷侧分段与双斜切胎架装配 | 19 | 15 |
| chapter5_018 | 艉部下段装配 | 22 | 16 |
| chapter5_025 | 分段制造精度标准 | 20 | 18 |
| 合计 | - | 93 | 79 |

人工标注文件为 `chapter5_rag/eval/gold_annotations.json`，摘要文件为 `gold_annotations_summary.json`。标注内容包括 gold_entities 和 gold_triples，每个实体包含 name、type 和 evidence，每条三元组包含 head、relation、tail 和 evidence。该标注集作为 Pangu 和 DeepSeek 抽取质量评测的 gold 标准。

### 5.2 评价指标设计

本文设计了实体级、三元组级、格式稳定性和证据可信度四类指标。

实体级指标包括 Precision、Recall 和 F1。实体匹配规则为实体名称完全一致或去空格后一致，同时在 relaxed 分析中允许少量别名和包含关系辅助判断。实体类型准确率用于衡量模型是否将实体归入正确类型，例如是否将“胎架”识别为工装设备，将“焊接变形”识别为质量问题。

三元组级指标包括 strict、relaxed 和 semantic-like 三种 F1。strict 三元组要求 head、relation、tail 三者完全匹配；relaxed 三元组允许关系同义词归一和实体别名匹配；semantic-like 指标在 relaxed 基础上进一步允许一定程度的字符重叠和语义近似，用于反映模型抽取的语义覆盖能力。

格式稳定性指标包括 JSON 合法率和抽取成功率。JSON 合法率表示模型 raw_response 是否能够解析为合法 JSON；抽取成功率表示该 chunk 是否成功得到实体或三元组。证据可信度指标包括 evidence 支撑率和幻觉率。evidence 支撑率衡量三元组证据是否能在原文中追溯；幻觉率衡量模型输出中无法由原文支持的实体或三元组比例。

### 5.3 第一轮抽取结果分析

第一轮抽取使用较基础的 Prompt，模型输出较为保守，抽取数量明显不足。基于 5 个 gold chunk 的评测结果如下：

| 模型 | 预测实体数 | 预测三元组数 | 实体 F1 | Strict 三元组 F1 | JSON 合法率 | 抽取成功率 |
|---|---:|---:|---:|---:|---:|---:|
| Pangu round1 | 23 | 22 | 36.21% | 3.96% | 100.00% | 100.00% |
| DeepSeek round1 | 25 | 28 | 33.90% | 0.00% | 100.00% | 100.00% |

从结果看，第一轮两个模型的 JSON 输出都比较稳定，但知识覆盖度不足。Pangu 实体 precision 较高，但 recall 低，说明其更倾向于抽取较确定的实体；DeepSeek 抽取数量略多，但 strict 三元组匹配仍然为 0。第一轮实验说明，普通 Prompt 难以满足高质量知识图谱构建要求，必须在 Prompt 中明确抽取数量、关系类型、证据字段和表格数据要求。

### 5.4 第二轮 Prompt 优化结果分析

第二轮 Prompt 优化后，模型抽取覆盖度显著提升。基于同一 gold 标准集，第二轮结果如下：

| 模型 | 预测实体数 | 预测三元组数 | 实体 F1 | Strict 三元组 F1 | Relaxed 三元组 F1 | Semantic-like F1 | JSON 合法率 | 抽取成功率 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Pangu round2 | 75 | 81 | 63.10% | 0.00% | 7.50% | 7.50% | 100.00% | 100.00% |
| DeepSeek round2 | 78 | 110 | 70.18% | 5.29% | 17.99% | 20.11% | 80.00% | 80.00% |

Pangu round2 的特点是输出稳定，JSON 合法率和抽取成功率均为 100%，evidence 支撑率为 97.53%，幻觉率为 1.92%。但 Pangu 抽取仍相对保守，实体召回和三元组召回仍有提升空间，strict 三元组 F1 为 0，说明其三元组表达与 gold 标注在关系名称、实体边界或粒度上存在较大差异。

DeepSeek round2 的特点是语义覆盖更好，实体 F1 达到 70.18%，relaxed 三元组 F1 达到 17.99%，semantic-like F1 达到 20.11%，均高于 Pangu。DeepSeek 抽取三元组数为 110 条，多于 Pangu 的 81 条，说明其更倾向于输出较丰富的关系。但 DeepSeek 在 `chapter5_012` 上输出不完整 JSON，导致 JSON 合法率和抽取成功率为 80%，幻觉率为 4.79%，高于 Pangu。

总体来看，Pangu 更稳定、更可控，适合强调本地部署和格式稳定的场景；DeepSeek 语义覆盖更强，但需要 JSON 修复、失败重试和人工复核机制来提高工程可用性。

### 5.5 DeepSeek 失败样本与重试分析

DeepSeek round2 中失败的 chunk 为 `chapter5_012`，该 chunk 内容包括带甲板边板的横骨架式舷侧分段、双斜切胎架、中心线和中间肋骨线、外板拼接、装配画线、舷侧纵桁、封底焊和完工检验等复杂流程。首次失败原因为 JSON 输出不完整：`Unexpected end of input`。

项目按照相同 Prompt、相同 schema、相同 timeout 和 retry 设置，只对 `chapter5_012` 做了一次补充重试实验，输出保存在 `outputs/round2_retry/deepseek/`。重试结果仍然失败，无法解析为合法 JSON，新增实体数为 0，新增三元组数为 0。因此 DeepSeek 抽取成功率未提升，仍为 80%。

该结果说明，复杂 chunk 中同时包含长流程、多个设备、多个构件和表格数据时，DeepSeek 容易出现结构化输出截断或 JSON 不完整问题。首次运行指标应作为模型稳定性的衡量结果，而 after_retry 指标只能作为加入失败重试机制后的系统可用性分析，不能替代首次运行结果。后续优化可以考虑缩短复杂 chunk、分阶段抽取实体和关系、增加 JSON 修复器、采用函数调用式 schema 约束，或引入多智能体校验机制。

## 第6章 不同实现方案性能与成本对比

### 6.1 对比方案设计

本文对比三种第五章 RAG 实现方案：

1. A_vector_rag：纯向量 RAG，不使用知识图谱，只对第五章文本块进行向量检索。
2. B_pangu_graph_rag：Pangu 抽取三元组，构建知识图谱，并与向量 RAG 融合。
3. C_deepseek_graph_rag：DeepSeek 抽取三元组，构建知识图谱，并与向量 RAG 融合。

三种方案使用相同的第五章语料和相同的 15 个测试问题集。测试问题覆盖概念定义类、工艺流程类、对比类、图纸资料类、质量控制类和表格数据类。由于生成阶段受远程模型稳定性影响，本次方案对比主要评测检索阶段性能，包括 Top1、Top3、Top5 命中率、关键词覆盖率和平均检索耗时。

### 6.2 图谱结构质量对比

基于 round2 抽取结果，对 Pangu 和 DeepSeek 图谱结构进行统计，结果如下：

| 方案 | 实体数 | 三元组数 | 关系类型数 | 平均度数 | 最大连通子图比例 | 孤立实体比例 | 泛化关系比例 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Pangu Graph-RAG | 120 | 81 | 43 | 1.3500 | 20.00% | 8.33% | 17.28% |
| DeepSeek Graph-RAG | 117 | 110 | 17 | 1.8803 | 52.14% | 9.40% | 24.55% |

Pangu 图谱关系类型数更多，说明其关系表达较分散，包含“工作量占比、适用场景、结构特点、装配方式、标准范围、装配程序包括”等多种关系。但最大连通子图比例只有 20.00%，说明图谱中存在较多局部子图，整体连通性偏弱。

DeepSeek 图谱三元组数更多，平均度数更高，最大连通子图比例达到 52.14%，说明其抽取的关系更容易形成较大连通网络。DeepSeek 的关系类型数为 17，低于 Pangu，关系表达更集中，但泛化关系比例为 24.55%，高于 Pangu，说明其较多使用“包括、属于、可以是”等泛化关系，需要进一步做关系精细化和归一化。

基于 15 个第五章测试问题，三种方案检索性能如下：

| 方案 | Top1 命中率 | Top3 命中率 | Top5 命中率 | 关键词覆盖率 | 平均检索耗时 |
|---|---:|---:|---:|---:|---:|
| A_vector_rag | 40.00% | 73.33% | 86.67% | 93.00% | 1.11 ms |
| B_pangu_graph_rag | 33.33% | 73.33% | 86.67% | 93.00% | 1.30 ms |
| C_deepseek_graph_rag | 33.33% | 73.33% | 86.67% | 93.00% | 1.37 ms |

从离线检索指标看，三种方案 Top5 命中率和关键词覆盖率一致，说明在第五章 29 个 chunk 的小规模语料上，纯向量检索已经能够较好召回相关文本块。Graph-RAG 在该检索评测中没有显著提高 Top5 命中率，但提供了额外的结构化证据，能够增强流程类、关系类和质量标准类问题的可解释性。

Graph-RAG 的平均检索耗时略高于纯向量 RAG，原因是其除文本块检索外，还需要进行三元组检索和证据融合。但在当前规模下，三种方案检索耗时均在毫秒级，性能差异很小。需要注意的是，本次未调用生成模型，因此未统计平均生成耗时和答案长度；这些指标在报告中标记为 N/A。

### 6.5 综合分析

综合性能和成本，三种方案各有适用场景。

纯向量 RAG 实现简单、构建速度快、成本最低。在第五章小规模语料上，纯向量 RAG 的 Top5 命中率和关键词覆盖率已经较高，适合作为系统基线或快速原型。但它缺少结构化知识，难以直接表达“工序包含哪些步骤”“某构件装配于哪里”“某质量问题由什么导致、如何控制”等关系型知识。

Pangu Graph-RAG 的优势是稳定可控。Pangu round2 JSON 合法率和抽取成功率均为 100%，适合需要自部署、数据可控和格式稳定的场景。不足是抽取较保守，三元组召回偏低，图谱最大连通子图比例较低，说明仍需要更强的实体归一化和关系融合。

DeepSeek Graph-RAG 的优势是语义覆盖较好。DeepSeek round2 实体 F1、relaxed 三元组 F1 和 semantic-like F1 均高于 Pangu，图谱连通性也更强。但其在复杂 chunk 上存在 JSON 输出不完整问题，输出稳定性略弱，需要重试、修复和人工复核机制。

## 第7章 结果讨论与优化建议

### 7.1 实验结果讨论

从整本书探索看，本项目已经完成从扫描版教材到 OCR 文本、清洗分块、知识抽取、知识图谱构建和 RAG 问答系统的完整流程。整本书级 Pangu 图谱形成 1003 个实体和 1747 条关系，说明该技术路线具备规模化构建能力。

从第五章精细化实验看，项目进一步完成了高质量文本整理、29 个 chunk 切分、Pangu 与 DeepSeek 双模型抽取、人工标注集构建、两轮 Prompt 对比、图谱结构评测、RAG 检索评测和成本评估。第五章实验比整本书探索更细，因为它引入了人工 gold 标准集和多指标评测，能够更真实地反映模型抽取质量。

实验结果表明，Graph-RAG 的价值不只体现在 Top-k 检索命中率上，更体现在结构化知识组织和可解释证据链上。对于第五章这样流程性强的章节，图谱能够把“分段类型-装配方式-构件-工序-工装设备-质量措施”连接起来，使系统更容易回答关系类和流程类问题。

### 7.2 系统不足

当前系统仍存在若干不足。

第一，OCR 和文本清洗成本较高。整本书扫描版 PDF 存在图表多、表格复杂、页码和图注混排等问题，OCR 后仍需要人工检查和局部修正。第五章之所以效果较好，很大程度上依赖精细化文本整理。

第二，三元组 strict F1 偏低。即使第二轮 Prompt 优化后，Pangu strict 三元组 F1 仍为 0，DeepSeek strict 三元组 F1 为 5.29%。这并不完全说明模型没有抽到知识，而是反映出模型输出与人工标注在实体边界、关系名称和表达粒度上差异较大。

第三，实体粒度不一致。例如模型可能同时抽取“舷侧分段”“带甲板边板的横骨架式舷侧分段”“横骨架式舷侧分段”等不同粒度实体。如果不做实体归一化，图谱中会出现语义相近但未合并的节点。

第四，关系表达不统一。模型可能使用“包括、包含、装配程序包括、可以是、装配方式”等表达相近关系，导致图谱关系类型分散或泛化关系比例偏高。

第五，图谱仍存在局部松散节点。Pangu round2 图谱最大连通子图比例为 20.00%，说明存在较多局部知识片段未能连接到核心流程。DeepSeek 图谱最大连通子图比例较高，但泛化关系比例也较高，需要在连通性和语义精确性之间进一步平衡。

第六，复杂 chunk 的 JSON 稳定性仍需优化。DeepSeek 在 `chapter5_012` 上首次抽取和补充重试均出现 JSON 不完整，说明复杂流程 chunk 可能超过模型稳定结构化输出能力，需要更细粒度切分或分阶段抽取。

### 7.3 优化方向

后续可以从以下方面优化系统。

第一，实体归一化。建立实体别名表和同义词规则，将“倒装/反装”“双斜切胎架/专用双斜切胎架”等实体合并，减少重复节点。

第二，关系归一化。将“采用、可采用、可以采用、装配方式为”等映射为统一关系，将“包括、包含、装配程序包括”按语义场景进一步区分为分类包含和流程包含。

第三，三元组证据校验。对每条三元组的 evidence 进行原文匹配，如果 evidence 不存在于 chunk 或 head/tail 无法在原文中找到，则标记为低置信度。

第四，低置信度三元组人工复核。对于关系泛化、实体粒度不一致、数值表达不一致和 evidence 不可追溯的三元组，生成候选列表，由人工进行确认或修正。

第五，缩短复杂 chunk。对于 `chapter5_012` 这种同时包含长流程、多个工装设备、多个构件和定位数据的 chunk，可以拆分为“流程抽取块”“工装定位块”“表格数据块”，减少模型输出截断风险。

第六，多阶段抽取流程。先抽实体，再抽关系，再抽表格数据，最后做证据校验和图谱合并，避免单次 Prompt 输出过长。

第七，多智能体协同抽取和校验。可以设计 ExtractorAgent、NormalizerAgent、EvidenceVerifierAgent、GraphBuilderAgent 和 ReviewerAgent，使不同智能体分别负责抽取、归一化、证据检查、图谱构建和低置信度复核。

第八，增强 Graph-RAG 评测。后续可以引入生成阶段评测，比较答案正确性、完整性、引用质量和用户可读性，并进一步分析 Graph-RAG 在流程类、关系类、质量标准类问题上的真实增益。

## 第8章 总结

本文围绕《中级船体装配工工艺学》完成了整本书级知识抽取探索，并以第五章“船体分段的装配”为核心进行了精细化知识图谱构建、知识抽取评测和 Graph-RAG 方案对比。

在整本书层面，项目完成了扫描版 PDF 的 OCR、格式转换、文本清洗和 RAG 分块，生成 230 个文本块，并使用 Pangu 7B 自部署模型构建了整本书级知识图谱，形成 1003 个实体和 1747 条关系。在第五章层面，项目整理出独立清洗文本，切分为 29 个 chunk，构建了 Pangu 和 DeepSeek 两套图谱，并实现了向量检索、图谱检索、多智能体执行链路和前端展示。

在 RAG 方案对比方面，纯向量 RAG 成本最低、实现最简单；Pangu Graph-RAG 稳定可控，适合自部署和数据安全要求较高的场景；DeepSeek Graph-RAG 语义覆盖较好，图谱连通性更强，但依赖外部 API 且需要处理输出稳定性问题。实验表明，Graph-RAG 在结构化知识表达、流程关系追溯和质量标准类问题上具有优势，但仍需要通过实体归一化、关系归一化、证据校验和输出稳定性优化进一步提高图谱质量。
